# MVP: шлюз гарантированной доставки уведомлений

Репозиторий пуст, строим с нуля. B2B API: отправка уведомлений с фолбэками и статистикой доставки. Все каналы — за единым интерфейсом.

## Структура (монолит, чистые слои)

```
heartbeat/
├── main.py                    # единственная точка входа
├── requirements.txt           # фиксированные версии
├── .env.example               # без секретов
├── config/
│   └── limits.yaml            # тарифы/лимиты — наружу, перечитывается по SIGHUP
├── app/
│   ├── domain/                # Message, DeliveryAttempt, Channel, статусы
│   ├── application/           # SendMessage, FallbackChain, GetDeliveryStats
│   ├── adapters/
│   │   ├── channels/          # NotificationChannel (протокол) + адаптеры:
│   │   │                      #   TelegramAdapter (рабочий, Bot API)
│   │   │                      #   MaxAdapter, SmsAdapter, CallAdapter, EmailAdapter (базовые реализации)
│   │   └── storage/           # Postgres-репозитории (SQLAlchemy + asyncpg)
│   ├── infrastructure/        # настройки, TTL-кеш, rate-limit из YAML, SIGHUP-reload
│   └── api/                   # POST /v1/messages, GET /v1/messages/{id}, GET /v1/stats, /healthz, /metrics
├── migrations/                # alembic
├── tests/
├── Dockerfile                 # multi-stage → distroless, ENTRYPOINT exec-формой
├── docker-compose.yml         # app + postgres + prometheus
├── .github/workflows/ci.yml   # ruff + pytest + сборка образа по тегам
└── README.md                  # перезапись + эксплуатационный раздел
```

## Ключевые решения

- **Каналы за интерфейсом:** протокол `NotificationChannel.send(message) -> DeliveryResult`. Базово пять каналов: **Telegram** — реальный клиент (Bot API, таймауты, retry); **SMS, звонок, email, Max** — каркасные адаптеры с корректным контрактом, HTTP-клиентом и конфигом провайдера, но с провайдером-заглушкой (сырой API Макс и SMS-шлюз подключим без изменения бизнес-логики). Регистрация каналов — реестр в DI-контейнере, фолбэк-цепочка настраивается на уровне конфига (`telegram → max → sms → call → email`).
- **Данные:** справочные и конфигурационные данные (клиенты, API-ключи, маршруты, лимиты, статусы сообщений) читаем из Postgres и держим в памяти приложения — TTL-кеш в `infrastructure/`, чтобы на каждый запрос в стор не бегать. Инвалидация — по TTL + по SIGHUP (перечитали YAML-лимиты, сбросили кеш).
- **Статистика доставки:** таблица `delivery_attempts` (message_id, channel, status, latency_ms, error, ts) — источник для `/v1/stats` и будущего кабинета.
- **Конфиг лимитов/тарифов:** `config/limits.yaml` примонтирован, SIGHUP → перечитали без пересборки. Distroless без шелла — поэтому ENTRYPOINT строго exec-формой, никакого `sh -c`.
- **Стек:** Python 3.11, FastAPI + uvicorn, SQLAlchemy 2 + asyncpg, alembic, pydantic-settings, httpx, prometheus-fastapi-instrumentator, pytest, ruff. Версии зафиксированы.
- **CI/эксплуатация:** ruff + pytest + образ только по тегам (никакого latest на прод); в README — два окружения (staging → prod), откат = redeploy предыдущего тега, ежедневный бэкап Postgres, алерт на заглохший heartbeat.

## Не входит (следующие заходы)

Личный кабинет с UI, боевые провайдеры SMS/звонков/email, реальный клиент API Макс, Nuitka single-binary.

## Порядок работ

1. Скелет: main.py, настройки, .env.example, requirements.
2. Домен + миграции + Postgres-репозитории + TTL-кеш.
3. Протокол каналов: TelegramAdapter + каркасы Max/SMS/Call/Email + фолбэк-оркестратор.
4. API-роуты, статистика, rate-limit из YAML с SIGHUP.
5. Тесты (оркестратор, адаптеры, API).
6. Dockerfile (distroless, exec-форма), docker-compose, CI, README.
